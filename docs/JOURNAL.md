# JOURNAL — 무엇을 재서 무엇이 나왔고 왜 그렇게 정했나

팀이 읽는 기록이다. 회차마다 **쟀다 → 나왔다 → 판단 → 넘어간 이유 → 아직 아니다** 를 남긴다.
이 서버의 설정값이 왜 그 값인지 궁금할 때 여기서부터 거슬러 올라가면 된다.

규칙: **새 회차는 맨 위에 붙인다. 지난 항목은 고치지 않는다.** 나중에 틀린 것으로 밝혀지면 새 항목에서 정정하고 이유를 적는다.
수치는 여기서 만들지 않는다 — `data/evaluation/runs/*.json` 이 정본이고 여기에는 run_id 와 함께 옮겨 적기만 한다.
개념 설명은 여기 쓰지 않는다. 필요하면 회차별 상세 문서로 링크한다.

## 2026-09-01 — `ast-v1` 은 "다른 청킹 방식"이 아니라 결함 버전이었다 (8/30 항목 정정)

**쟀다.** 8/30 항목은 `ast-v1` 과 `ast-v2` 를 "청커가 다른 실험 셀" 로 적었다. 그 표현이 맞는지 두 청커에 같은 소스를 넣어 직접 돌렸다.

**나왔다.** 두 가지가 나왔다.

- 제어문 아래 정의를 통째로 놓친다. `try/except` 로 import 를 감싸고 `if` 아래 함수를 두 벌 정의한 파일에서 `ast-v1` 이 찾은 심볼은 클래스 하나뿐이었고, 함수 둘은 아예 안 잡혔다.
- 청크가 크기로 갈릴 때 **맥락 헤더가 다른 함수 이름을 단다.** 함수 두 개짜리 파일에서 `ast-v1` 이 낸 두 번째 청크는 헤더가 `# x.py > def parse_fallback` 인데 담긴 코드는 대부분 그다음 함수였고, 시작 위치도 줄 중간이었다.

**판단.** 둘째가 검색에 직접 걸린다. 맥락 헤더는 청크 본문에 붙어 그대로 임베딩되므로(`VSS_CONTEXT_HEADER=on`, 8/27 [제안 E]), 틀린 이름이 벡터에 섞여 있다. 이건 두 설계의 차이가 아니라 한쪽의 결함이다.
따라서 **8/27 `--ast` run 2건은 "개선 전" 기준선으로 인용하지 않는다.** 대신 `--lines` 인덱스가 기준선을 맡는다 — 줄 윈도우 경로는 `python_nodes` 를 거치지 않아(`vss/chunker.py`) 이 결함과 무관하고, 8/27 수치가 그대로 유효하다.

**넘어간 이유.** 지금 서비스 중인 인덱스 4개가 모두 `ast-v1` 이라, 어떤 개선 수치도 재인덱싱 전에는 말할 수 없다. 청커 코드는 8/31 커밋(`9a97d87`)으로 이미 고쳐져 있고 남은 것은 EC2 재인덱싱 하나다.
`ast-v1` 구현 자체는 지우지 않고 동결해 둔다. 8/27 run 이 저장한 fingerprint 가 가리키는 코퍼스를 재현할 수 있어야 "왜 그 수치를 안 쓰는가" 를 보일 수 있다.

**아직 아니다.** `ast-v2` 전체 재인덱싱과 같은 suite 재측정. 그 전까지 비교 대상은 `--lines` ↔ `--ast(ast-v2)` 이고, `ast-v1` 은 어느 쪽 표에도 올리지 않는다.

## 2026-08-30 — 같은 fingerprint의 코퍼스를 바꾸지 않고 AST 누락을 `ast-v2`로 분리했다

측정 회차가 아니다. Python AST 추출의 재현 결함을 고치고, 과거 기준선의 의미를 보존하는 호환 경계를 코드와 테스트로 고정한 회차다.

**쟀다**

- `python_nodes`에 제어문 아래 함수, 팩토리 내부 핸들러, 중첩 클래스가 들어오는지 최소 fixture로 직접 비교
- Claude Code가 바꾼 라우트 AST 추출에서 set·동적 `methods=`와 비라우터 데코레이터가 정확히 처리되는지 집중 회귀 테스트

**나왔다**

- `ast-v1`은 fixture에서 최상위 `factory`와 `Outer`만 반환했다. `if`·`try/except` 아래 함수와 `factory.handler`, `Outer.Config` 아래 심볼은 독립 청크가 아니었다.
- 새 라우트 추출은 `methods={"POST", "PUT"}`을 기본 GET으로 오보고하고, `methods=["POST", METHOD]`에서는 동적 요소를 버렸다. `api_route`의 methods 생략도 실제 기본 GET 대신 ANY로 기록했다.
- 메서드명과 `/` 경로만 확인하면 `@pook.get("/users")`·`@pytest.mark.get("/integration")`도 라우트로 오인했고, mock 객체를 `api` 변수에 담으면 이름 휴리스틱을 우회했다.

**판단**

- 기존 구현은 `_python_nodes_v1`로 동결하고, lexical scope를 유지하며 재귀 순회하는 `_python_nodes_v2`를 별도로 추가했다. 기본 청커는 `ast-v2`지만 명시적 `ast-v1`은 이전 코퍼스를 그대로 만든다. 클래스 선언은 독립 청크로 남기고, 부모 함수에서는 중첩 정의 본문을 줄 수 보존 placeholder로 바꿔 이중 가중을 막는다.
- `chunker` 값 자체가 fingerprint에 있으므로 `CORPUS_RULES`는 올리지 않았다. `ast-v1`과 `ast-v2` 결과를 같은 조건으로 취급하지 않는다.
- 라우트 메서드는 set을 포함한 정적 컨테이너를 처리하고, 동적 식을 부분 손실하지 않으며 `api_route` 생략값을 GET으로 기록한다. 라우트 객체는 프레임워크 생성자 대입과 app/router 계열 이름으로 제한하되 명시적인 test/mock 생성자 대입은 제외한다. 브리핑은 중첩 symbol의 전체 qualified name을 표시한다.

**넘어간 이유**

검색 코퍼스를 바꾸는 수정이므로 버전 경계를 먼저 세워야 했다. 이전 평가를 소급해 다른 코퍼스의 결과로 만드는 것보다 새 fingerprint로 전체 재인덱싱하는 비용이 작고 추적 가능하다.

**아직 아니다**

- EC2의 기존 인덱스는 모두 `ast-v1`이다. `ast-v2` 전체 재인덱싱과 동일 suite 재측정은 md가 EC2에서 실행해야 한다.
- 이 회차는 검색 품질 수치를 만들지 않았다. 개선 여부는 저장된 `ast-v2` fingerprint와 고정 코퍼스 revision이 들어간 새 run으로만 판정한다.

- 외부 코드 리뷰가 지적한 질의 흐름 결함 7건이 실제로 재현되는가 — 재현 스크립트 실행 + 각 지점 코드 대조

**나왔다**

- **`project_id` 별칭은 코드가 아니라 설정 문제였다.** 별칭 코드는 EC2 가 서 있던 커밋에 이미 있었고, `.env` 에 `VSS_PROJECT_ALIASES` 한 줄이 없었다.
  넣은 뒤 `{"project_id": "api_test", "index_id": "api-test--ast"}` 확인. `api_test`·`api-test`·`API_TEST` 가 모두 같은 곳으로 가고, 없는 이름은 조용히 넘어가지 않고 `project_not_found` 다.
- **결함 7건 전부 사실이었다.** 그중 가장 심한 것: 모델이 없는 번호(`[7]`)를 인용하거나 답변에 `items[0]` 같은 코드 표기만 있으면
  **출처 목록이 통째로 빈 배열이 됐다.** 본문에는 각주 번호가 보이는데 출처가 없는 화면이 된다.
- 리뷰에 없던 것도 나왔다: 최종 응답의 `timing` 이 검색 구간만 실어 **`prompt_ms` 가 애초에 응답에 오지 않았고**, 계약 문서는 온다고 적혀 있었다.

**판단**

- 출처 전멸(D·E)은 **코드로 고쳤다** — 인용 번호를 `contexts` 범위로 거른다. 범위 밖만 인용하면 "인용 0건" 과 같게 취급해 전부 유지한다. `[N]` 번호는 재부여하지 않는다(불변 조건 4).
- `prompt_ms` 는 **이름과 구간을 맞췄다** — `prompt_ms` 는 프롬프트 조립만, `pre_llm_ms`(신설)가 요청~LLM직전 누적이다. 발표에 타이밍을 쓸 계획이 있어 지금 바로잡았다.
- 나머지 셋(`has_evidence` 의 뜻 · 스트리밍의 HTTP 상태 · `rag:false` 의 meta 모양)은 **동작을 바꾸지 않고 계약에 명시**했다. 9/9 동결이 가깝고, 셋 다 "현재 동작이 무엇인지 몰라서" 생기는 문제였다.

**넘어간 이유**

계약을 K·Y 에게 넘기는 날이라, 프론트가 잘못 분기할 수 있는 지점을 먼저 닫아야 했다. 특히 `metadata.has_evidence`(검색 단계)와 `no_evidence`(최종 결과)는
**한 응답에서 둘 다 true 가 정상적으로 나온다** — "근거는 찾았지만 그것으로 답할 수 없었다" 는 뜻이다. 여기서 잘못 분기하면 "근거 없음" 화면이 뜨지 않는다. `docs/API.md` 에 표로 넣었다.

**아직 아니다**

- **답이 나와야 할 질문에 "근거 없음"이 나온다.** api_test 에 실제로 있는 주제(`worker`)를 물어도 `NO_EVIDENCE` 였다. 검색이 막힌 건지 모델이 거절한 건지 아직 가르지 못했다.
  관련 신호: 코퍼스와 무관한 질문조차 `top_score 0.5996` 으로 임계값 0.54 를 넘는다 — 이 코퍼스에서 임계값이 거의 걸러 내지 못한다는 뜻이다. 9/4 고정 질문 선정 전에 풀어야 한다.
- `api_test` gold 는 아직 8문항이라 이 코퍼스의 정확도를 판정할 수 없다(1문항 = 16.7%p). 40문항이 임계 경로다.
- 오늘 수정은 아직 EC2 에 반영되지 않았다 — 도는 서버는 이전 커밋이다.
