## 4. 설계 판단이 갈린 곳 둘

- **think 값을 모델이 거부할 때** — 검토자: 지원 여부를 미리 확인. 채택: 즉시 실패(`think_unsupported`)하고 설정을 바꾸라고 알림. 확인 호출이 하나 더 드는 것과 조용한 fallback 을 피하려고.
- **생성 중 소스 변경** — 검토자: 소스 고정 전까지 발행 차단 유지. 채택: 조사 직후 재검사로 섞인 버전을 막고, 그 뒤 변경은 `source_changed` 표시로 발행. 조사는 파일을 한 번에 읽어 메모리만 쓰므로 그 뒤 변경은 분석을 섞지 않고 오래되게만 한다.

### 4.1 검토에서 걸러진 수정안 (처음 안 → 바뀐 안)

코드로 확인해 보니 첫 수정안 중 열 개가 틀리거나 성급했다. 어떤 것이 왜 걸러졌는지가 이 조정의 절반이다.

| 처음 안 | 문제 | 바뀐 안 |
|---|---|---|
| 브리핑만 thinking 을 끈다 | 단계 캐시 키가 전역 설정을 써서 옛 값으로 만든 결과가 재사용된다 | 캐시 키에 실효값을 넣는다 |
| 근거 id 가 틀린 것만 빼고 문장은 살린다 | 한 문장에 사실 둘이면 남은 근거가 뒷받침 못 한다 | 틀린 id 가 든 문장은 통째로 뺀다, 손실은 `partial` 로 표시 |
| 전송 오류는 전부 단계 실패로 감싼다 | 캐시 쓰기·프로그래밍 오류까지 삼킨다 | LLM 호출만 좁게 감싸고 1회 재시도 |
| 계수는 "약 2배" 라 4 묶음이면 지금 6~8 묶음과 같다 | 잰 값이 아니었다 | 실측 뒤 정하고 문서 묶음 수는 6 유지 |
| 예산 0 이면 항상 final 로 부분 결과 | 분석이 0 이면 final 이 호출 전에 실패하는 게 기존 로직 | 그 동작 유지, 테스트를 바꿈 |
| 고정 주제는 경로가 비면 뺀다 | `store.save()`·권한 검사처럼 호출로 드러나는 근거를 잃는다 | 후보 출처(경로·정의·호출·검색)로 판정, 본문 한 줄 일치뿐이면 호출 안 함 |
| README 를 전부 먼저 읽는다 | 긴 README 가 묶음 6개를 다 차지해 다른 문서를 밀어낸다 | README 첫 조각과 중요 절만 먼저, 파일당 묶음 절반 |
| 진입점·라우트를 옛 추출기 결과로 통째로 바꾼다 | 행 모양이 달라 `KeyError`, typer `@app.command` 같은 비 HTTP 등록을 잃는다 | HTTP 행만 바꾸고 키 매핑, 나머지 등록은 유지 |
| 본문에서 뺀 단계 기록은 JSON 에 있다 | `result.json` 에 `problems` 가 없었다 | 키를 추가 |
| busy 때 빈 폴더가 생기니 `mkdir` 한 줄 삭제 | 그 줄이 lock 의 부모 폴더도 만든다 | 부모는 먼저, run 폴더는 lock 뒤 |

검토자의 순서 제안도 받았다 — lock 복구(②)를 품질 작업보다 앞에. 실제 모델을 반복 실행하는 동안 재시작 한 번이면 이후가 전부 busy 가 되기 때문이다.

### 4.2 결정에 쓴 재료

- **함수 헤더를 넣을지 (넣기로)** — 데모 레포에서 진입점 파일의 최상위 함수·클래스 수를 셌다: api_test 8개 파일 중 `backend/app.py` 5, `worker.py` 4, `ingest.py` 3, **`legacy_app.py` 172**(대부분 라우트 핸들러); fastapi-new 5개 파일 ≤9; flask 예제 `app.py` 6; TypeScript 레포 0(추출 없음). 라우트 핸들러를 빼면 파일당 10개로 충분하고 LLM 비용은 0.
- **실행 기록을 몇 개 남길지 (3 + 발행 run)** — `analysis.json` 크기를 쟀다: fastapi-new 0.1 MB, api_test 3.0 MB, sqlalchemy 급 41 MB(대부분 호출·import 목록 33 MB). 이 파일을 호출마다 다시 쓰고 있어서 sqlalchemy 급이면 run 당 1.6 GB 쓰기 → 정적 부분을 `survey.json` 에 한 번만 쓰도록 바꿨다(호출당 0.3 MB).
- **생성 중 소스가 바뀌면 (표시하고 발행)** — 두 시나리오를 짚었다. Extension 경로는 브랜치가 달라도 `~/repos/<레포>` 한 폴더를 써서 도중에 checkout 이 일어날 수 있고, 스냅샷 백엔드는 같은 브랜치의 새 commit 이 오면 같은 이름으로 전체 인덱싱을 다시 부른다 — 그때 이전 run 은 끝에서 버려지고 새 훅은 lock 에 걸려 둘 다 잃는다. 조사는 파일을 한 번에 읽어 메모리만 쓰므로 섞임은 조사 몇 초 사이에만 생긴다 → 조사 직후 재검사로 막고, 그 뒤 변경은 표시.
- **병합 호출을 없앨지 (보류)** — 최대 구성에서 호출 38 → 28회. 상세 절 품질을 비교한 뒤 정하기로 하고, ⑫ 에서 실패 시 이어 붙이기만 넣었다.

### 5.1 1회차 — 무엇을 봤나, 그래서 무엇을 고쳤나 (→ ⑩)

### 5.2 2회차 — (→ ⑪)

주제 8개 전부 조사, 순서도 의도대로, 라우트 절도 명령 5줄 + 생략 1줄. 그런데 문서 요약에 README 가 없어졌다. 실행 기록에 `documents batch 0 output_truncated` — README 와 릴리스 노트 앞부분이 든 첫 묶음이 **두 번 다 1200토큰에 잘려** 버려졌고, 둘째 묶음도 한 번 잘리고 재시도로 넘어갔다. 원인은 내가 정한 1200 이 모자란 것 — 계수를 낮춘 만큼 묶음에 글이 두 배 들어가 답도 길어졌는데, 형식은 주제 조사와 같은 배열 5개(설명·조건·흐름·읽을 위치·요약)였다. "8개까지" 지시로는 모델이 충분히 줄이지 않았다.
계수: 코드 위주 호출은 0.73~0.85 인데 **마크다운 호출은 1.06~1.10** — 어림보다 실제가 많았다. 링크·기호가 많은 글은 토큰이 더 든다. 예비 공간 덕에 넘치진 않았지만 "여유 17%" 는 마크다운엔 틀린 말이었다. 최소제곱 3.19/0.46.
→ ⑪: 문서 호출 전용 형식(배열 3개, 6개까지)·출력 1500, 계수 **2.8/0.6**(마크다운 2.6자/토큰에 맞춤).

### 5.3 3회차 — (→ ⑫, 아직 실행 전)

문서 3회 86초, 잘림 0, README 6줄이 요약 맨 앞. 주제 8개 전부 + 보완 라운드 진입 — 첫 주제가 미확인 항목으로 검색을 2번 더 해 근거 12조각으로 재분석을 시도했는데 마지막 병합 호출이 30초 만에 시간 초과. 모델이 느린 게 아니라 규칙 탓: 남은 예산이 적으면 호출 제한 시간을 "남은 시간 − final 몫" 으로 주고 하한이 30초라, 보통 27~35초 걸리는 호출을 30초 제한으로 시작해 놓고 실패시켰다. 30초를 쓰고 얻은 것이 없다.
계수 2.8/0.6 으로 비율 0.68~1.04(마크다운 1.04) — 예비 공간 20% 안이라 유지. "확인이 필요한 사항" 에 같은 문장이 끝말만 다르게 두 번씩(최종 정리가 주제별 미확인을 다시 적음). 문서 요약 15줄 중 9줄이 여전히 릴리스 노트(README 1묶음, 릴리스 노트 2묶음).
→ ⑫: 남은 시간 60초 미만이면 호출 시작 안 함, 병합 실패 시 두 분석 이어 붙임, 미확인 중복 제거(앞 20글자), 변경 이력 문서는 묶음 1개까지.

테스트 수 변화: 124(시작) → 127(인덱싱 옮김) → 131 → 138 → 142 → 146 → 151 → 153 → 157 → 158 → 159 → 160 → 161 → 165(⑫). 세션 중 전체 실행 약 30회, 실패는 chat 경로의 알려진 간헐 503 3회와 테스트 자체 오류 4회(코드 아닌 테스트 수정)뿐이다.

## 6. 토큰 어림 계수 실측

호출마다 입력의 ASCII 글자 수·그 밖 글자 수와 Ollama 가 센 실제 토큰(`prompt_eval_count`)을 기록하고 최소제곱으로 맞췄다.

| run | 호출 | 실제/어림 비율 | ASCII (자/토큰) | 그 밖 (토큰/자) |
|---|---|---|---|---|
| 1회차 (어림 2 / 2) | 15 | 0.39~0.58, 평균 0.48 | 3.51 | 0.59 |
| 2회차 (어림 3.0 / 0.7) | 17 | 0.73~1.10, 평균 0.84 | 3.19 | 0.46 |
| 3회차 (어림 2.8 / 0.6) | 17 | 0.68~1.04, 평균 0.79 | 3.32 | 0.52 |

코드 위주 호출은 영문 3.3~3.5자가 1토큰이고, 링크·기호가 많은 마크다운(release-notes)은 2.6자까지 내려간다. 채택값은 마크다운에 맞춘 **영문 2.8자/토큰, 그 밖 0.6토큰/자** (`VSS_BRIEFING_CHARS_PER_TOKEN_ASCII`, `VSS_BRIEFING_TOKENS_PER_CHAR_OTHER`). 옛 값(2/2)보다 호출당 자료가 약 1.4배 들어간다. 표본은 한 레포라 한글 비율이 다른 레포(api_test)로 확인이 남아 있다.

## 8. 실행 기록에서 숫자를 보는 법 (재현용)

`data/briefings/runs/<인덱스>/<run_id>/analysis.json` 하나면 5·6절의 표를 다시 만들 수 있다.

| 표의 숫자 | 어디서 |
|---|---|
| 총 시간 | 같은 폴더 `result.json` 의 `elapsed_s` (CLI 는 끝에 `(저장: …, 531.9s, model=…)` 로도 찍는다) |
| LLM 호출 수·단계별 시간 | `calls[]` — `stage`(documents/plan/topic/topic_merge/final), `attempt`, `elapsed_s`. `cache: true` 항목은 호출이 아니다 |
| 어림 토큰·실제 토큰·글자 수 | `calls[].input_estimate`, `prompt_eval_count`(Ollama 실측), `chars_ascii`, `chars_other`. 계수는 `actual ≈ chars_ascii / A + chars_other × B` 를 최소제곱으로 |
| 출력 잘림·시간 초과 | `calls[].done_reason`(`length` 면 잘림), `calls[].error`(`output_truncated`, `llm_timeout`, `invalid_response` …) |
| 주제 조사 수 | `analyses[]` 의 `status`(analyzed/failed) 와 `error`, 보완은 `repaired`·`repair_error` |
| 문서 묶음과 근거 출처 | `documents[]`(묶음별 근거 id), `evidence[]`(id → path·줄 범위·type) |
| 검색 활용 | `retrieval[]` — 질의, `candidates`, `adopted`, `reason` |
| 부분 결과 사유 | `problems[]` 의 `reason` |
