## 1. RAG 가 무엇을 하는가

질문이 들어오면 서버는 이 순서로 답을 만든다.

```
질문 ──1)임베딩──▶ 숫자 벡터 1024개
                      │
                      2)벡터 검색 (코사인 유사도)
                      ▼
              후보 청크 20개 (pool)
                      │
                      3)근거 있음/없음 판정   ← 최고 점수가 임계값을 넘는가
                      ▼
              근거 4개 [1][2][3][4]
                      │
                      4)프롬프트 조립 → LLM → 답변 + 인용 [N]
```

핵심은 **실패 지점이 서로 독립된 두 개**라는 것이다.

- **찾기 실패** — 정답이 있는데 검색이 못 찾았다. (2번 문제)
- **판단 실패** — 정답이 없는데 있다고 하거나, 있는데 없다고 했다. (3번 문제)

이 둘은 원인도 처방도 다르다. 그래서 **따로 잰다.** 오늘 측정이 두 벌(`retrieval` / `pipeline`)인 이유가 이것이다.

## 2. 오늘 쓴 용어

### 데이터를 만드는 쪽

| 용어 | 뜻 | 왜 있나 |
|---|---|---|
| **청크(chunk)** | 파일을 잘라 만든 조각. 검색·인용의 최소 단위 | 파일 전체는 너무 크고, 한 줄은 너무 작다 |
| **청킹 방식** | 어떻게 자르는가. `line-window-v1`(줄 단위 기계적) / `ast-v1`(함수·클래스 단위) | 자르는 방식이 검색 품질을 결정한다 — 오늘의 주 실험 |
| **맥락 헤더** | 청크 앞에 `파일경로 · 심볼명` 을 붙이는 것 | 조각만 보면 어디 것인지 모른다. 붙이면 유사도가 오른다 |
| **임베딩** | 글을 1024개 숫자로 바꾼 것 | 숫자끼리는 "얼마나 비슷한가"를 계산할 수 있다 |
| **코사인 유사도** | 두 벡터가 얼마나 같은 방향인가. 0~1 | 이 값이 곧 검색 점수다 |
| **BM25** | 단어가 겹치는 정도로 매기는 옛 방식 검색 | 벡터가 놓치는 정확한 심볼명을 잡는다 |
| **RRF 융합** | 벡터 순위와 BM25 순위를 섞어 재정렬 | **순서만 바꾼다.** 근거 있음/없음 판정은 벡터 점수로만 한다 |
| **fingerprint** | 그 인덱스를 만든 조건 전부(모델·청킹·제외규칙…)를 인덱스 안에 박아 둔 것 | 조건이 다르면 다른 인덱스다. 같은 fingerprint 끼리만 비교한다 |

### 채점하는 쪽

| 용어 | 뜻 |
|---|---|
| **gold(문제지)** | 질문 + 정답이 있는 파일·줄 범위. 채점 기준 |
| **answerable** | 코퍼스 안에 답이 있는 질문인가 |
| **hard negative** | 일부러 답이 없는 질문. *"이 프로젝트에서 사용자 로그인은 어떻게 처리하나요?"* → **"근거 없음"이라고 답해야 정답** |
| **Hit@3** | 정답 청크가 상위 3위 안에 들어온 질문의 비율 |
| **MRR** | 정답의 순위를 역수로 평균. 1위=1.0, 2위=0.5, 3위=0.33. 순위 품질을 한 숫자로 |
| **top_score** | 그 질문의 후보 중 **최고 벡터 점수** |
| **임계값(threshold)** | `top_score >= 임계값` 이면 "근거 있음". 현재 **0.54** |
| **gate recall** | 답이 있는 질문 중 임계값을 통과한 비율. 낮으면 헛되이 "근거 없음" 화면이 뜬다 |
| **no-evidence recall** | 답이 없는 질문 중 제대로 막은 비율. 낮으면 근거 없이 답하려 든다 |
| **balanced accuracy** | 위 둘의 평균. 임계값의 종합 성적 |

### 두 가지 측정 모드 — 이 구분이 오늘의 핵심

| 모드 | 무엇을 재나 | 임계값 적용 |
|---|---|---|
| **retrieval** | **찾기 능력만.** 정답이 몇 위에 있는가 | ❌ 안 함 |
| **pipeline** | **실제 서비스 전체.** 판정까지 거친 최종 결과 | ✅ 함 |

두 값의 차이가 곧 "임계값이 얼마나 깎아먹는가"다.

### 노이즈선 — 문항 수가 곧 해상도다

**문항 하나가 움직이는 폭 = 1/n.** 46문항이면 1문항 = 2.2%p. 그보다 작은 차이는 **우연과 구분할 수 없다.**
6문항짜리 측정에서는 1문항이 16.7%p 를 움직여, 어떤 결론도 낼 수 없다. (2026-08-25 에 실제로 겪은 사고)

각 단계마다 **무엇을 했나 / 무엇이 증명됐나 / 왜 다음으로 넘어갔나** 를 적는다.

### 단계 1. 저장소 결정 — Chroma 대신 pgvector

**한 일**: EC2 에 PostgreSQL 14 + pgvector 를 설치하고 검증했다.

**증명된 것**
- `CREATE EXTENSION vector` 성공, pgvector **0.8.6**
- 스키마 `rag`(우리) · `snapshot`(P) 생성, 소유자 분리 확인
- **왕복 테스트 10/10** — 실제 PostgreSQL 에 벡터를 넣고 빌드→승격→검색→재인덱싱→복구까지 통과

**왜 넘어갔나 (판단)**
원래 계획은 *Chroma 로 먼저 재고 → pgvector 로 바꾼 뒤 다시 재서 수치가 같은지 확인* 이었다. 그 대조의 목적은 **"저장소를 바꿔도 검색이 안 깨지는가"** 하나였는데, 위 왕복 테스트가 그것을 이미 증명한다.
그래서 Chroma 6개를 만들지 않았다. **인덱싱을 두 번 돌리는 GPU 비용(약 2시간)을 아꼈고**, Chroma 의 "한 프로세스만 열 수 있다"는 제약도 피했다(서버를 켠 채로 인덱싱할 수 있다).

> 근사 검색(hnsw)이 정확도를 깎는지는 재인덱싱 없이 `VSS_PG_EXACT=1` 로 **질의만 다시 해서** 확인할 수 있다. 아직 안 했다 → 5장.

### 단계 2. 코퍼스 배치 — 줄바꿈 사고와 복원

**한 일**: 데모 레포를 EC2 `~/repos/` 에 올렸다.

**무엇이 잘못됐나**
첫 인덱싱 결과에 `"dirty": true` 가 찍혔다. 노트북 원본은 깨끗했는데 EC2 사본에 변경이 있다는 뜻이다. 확인해 보니:

```
368 files changed, 81894 insertions(+), 81894 deletions(-)
```

**삽입과 삭제가 정확히 같다** = 줄 수는 그대로인데 모든 줄이 바뀌었다 = **줄바꿈 문자만 바뀐 것**. WinSCP 가 텍스트 모드로 전송하며 CRLF↔LF 를 변환했다.

**왜 이게 중요한가**
측정의 전제는 **"어느 코퍼스를 쟀는지 특정할 수 있다"** 이다. 파일 내용이 커밋과 다르면 `commit=2dea3d71` 이라는 기록이 실제 내용을 설명하지 못한다. 나중에 "이 수치는 무엇을 쟀나"에 답할 수 없어진다.

**어떻게 고쳤나**: `.git` 폴더가 함께 올라왔으므로 재전송 없이 복원했다.
```bash
git -C ~/repos/api_test checkout -- .
```

**증명된 것**: 재인덱싱 후 인덱스 4개 모두 `dirty=false`, `commit` 이 노트북 원본과 일치.
→ **코퍼스가 커밋된 트리와 바이트 단위로 같다.** 이제 측정을 시작해도 된다.

### 단계 3. 인덱싱 — 같은 레포를 왜 두 벌 만드는가

**한 일**: 레포 2개 × 청킹 방식 2개 = 인덱스 4개.

| 인덱스 | 청킹 | 맥락 헤더 | 청크 수 | 역할 |
|---|---|---|---|---|
| `fastapi-cli--lines` | line-window-v1 | 끔 | 250 | **대조군** |
| `fastapi-cli--ast` | ast-v1 | 켬 | 306 | **실험군** |
| `api-test--lines` | line-window-v1 | 끔 | 1,622 | 대조군 |
| `api-test--ast` | ast-v1 | 켬 | 1,674 | 실험군 |

**왜 두 벌인가**: 이것이 **대조 실험**이기 때문이다. "AST 청킹이 더 낫다"는 주장은 같은 레포·같은 질문지로 두 방식을 재서 비교해야만 증명된다. 하나만 만들면 비교 대상이 없어 아무것도 증명되지 않는다.

**왜 딱 이 두 축인가**: 인덱스를 새로 만들어야 하는 것은 **fingerprint 에 들어가는 값**(청킹 방식·헤더·제외 규칙·임베딩 모델)뿐이다. `top_k`·임계값·BM25 융합·생성 모델은 **같은 인덱스에 질의할 때** 바꾼다 → 인덱스를 늘릴 필요가 없다. 그래서 4개면 충분하다.

**한 일**: gold 61문항(답 46 + hard negative 15)으로 `fastapi-cli` 를, 8문항으로 `api-test` 를 측정.

**결과 (fastapi-cli, n=46, 노이즈선 2.2%p)**

*retrieval — 찾기 능력만*

| 인덱스 · 검색 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|
| lines · vector | 19.6% (9문항) | 45.7% (21) | 0.362 |
| lines · hybrid | 28.3% (13) | 52.2% (24) | 0.445 |
| **ast+header · vector** | **41.3% (19)** | 56.5% (26) | **0.519** |
| **ast+header · hybrid** | 37.0% (17) | **58.7% (27)** | 0.508 |

*pipeline — 임계값까지 거친 실제 결과*

| 인덱스 · 검색 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|
| lines · vector | 19.6% | 41.3% | 0.301 |
| lines · hybrid | 23.9% | 41.3% | 0.330 |
| ast+header · vector | 37.0% | 47.8% | 0.433 |
| ast+header · hybrid | 32.6% | 47.8% | 0.400 |

#### 증명된 것 ①: AST 청킹 + 맥락 헤더가 명확히 낫다

`lines · vector` → `ast+header · vector` 기준:

- **Hit@1 이 9문항 → 19문항.** +21.7%p, 노이즈선의 **10배**
- **Hit@3** 45.7% → 56.5%. +10.9%p, 노이즈선의 **5배**
- **MRR** 0.362 → 0.519

우연으로 설명할 수 없는 크기다. **함수·클래스 단위로 자르고 경로·심볼을 머리에 붙이는 것이 검색을 실제로 개선한다.**

> 왜 그런가(해석): 줄 단위로 자르면 함수가 중간에서 끊겨 조각만으로는 무엇인지 알 수 없다. 함수 단위로 자르면 한 조각이 하나의 완결된 의미를 갖고, 헤더가 붙으면 그 조각이 "어느 파일의 무슨 함수인지"까지 담는다. 질문이 대개 심볼 이름을 포함하므로 유사도가 오른다.

#### 증명된 것 ②: BM25 하이브리드의 이득은 AST 위에서 사라진다

| | Hit@1 | Hit@3 | MRR |
|---|---|---|---|
| lines: vector → hybrid | +8.7%p | **+6.5%p** | +0.083 |
| ast: vector → hybrid | **−4.3%p** | +2.2%p (=1문항, 노이즈) | −0.011 |

`lines` 에서는 확실히 도움이 되지만, `ast+header` 에서는 **이득이 노이즈 수준이고 Hit@1 은 오히려 내려간다.**

> 해석: 맥락 헤더가 심볼명을 청크 본문에 넣어 버리기 때문에, BM25 가 하던 "정확한 단어 매칭" 역할을 벡터 검색이 이미 흡수했다.

**이것이 판단에 주는 영향**: 발표에서 *"하이브리드 검색 덕분에 좋아졌다"* 고 말하면 **사실과 다르다.** 개선의 원인은 AST 청킹과 맥락 헤더다. BM25 는 켜 두되(손해는 없다) 공로를 돌리지 않는다.

#### 증명되지 않은 것: api_test 결과

| 인덱스 · 검색 | Hit@3 |
|---|---|
| lines · vector | 66.7% |
| ast+header · vector | 50.0% |

AST 가 더 나빠 보이지만 **n=6 이고 그 차이는 정확히 1문항**이다. 문항 하나가 16.7%p 를 움직인다.
**이 표는 판정에 쓸 수 없다.** "api_test 에서는 AST 가 나쁘다"고 읽으면 안 된다. 팀원의 40문항 gold 가 들어온 뒤 다시 재야 한다.

### 단계 5. 임계값 검증 — 0.54 는 맞는 값인가

**왜 이걸 했나**: pipeline 이 retrieval 보다 항상 낮았다. `ast+header · hybrid` 는 58.7% → 47.8%, **10.9%p(5문항)** 차이. **제대로 찾아 놓고 "근거 없음"으로 버린 문항이 있다**는 뜻이다. 임계값이 너무 높은 것 아닌가?

**어떻게 확인했나**: `python -m vss.eval sweep <run_id>`
run 파일에는 문항마다 `top_score` 와 `answerable` 이 저장돼 있고, 판정은 `top_score >= 임계값` 비교 하나뿐이다. 그래서 **임계값만 바꿔 다시 세면 된다** — 재인덱싱도 재질의도 필요 없는 산수다.

**결과 (`ast+header · vector`, 답있음 46 · 답없음 15)**

| 임계값 | 통과/답있음 | 막음/답없음 | Hit@3 | balanced acc |
|---|---|---|---|---|
| 0.46 | 45/46 | 4/15 | 56.5% | 62.2% |
| 0.50 | 43/46 | 11/15 | 54.3% | 83.4% |
| 0.52 | 42/46 | 12/15 | 52.2% | 85.7% |
| **0.54** | **41/46** | **14/15** | **50.0%** | **91.2%** ← 최고 |
| 0.56 | 39/46 | 14/15 | 47.8% | 89.1% |
| 0.58 | 34/46 | 15/15 | 43.5% | 87.0% |

**증명된 것: 0.54 는 이미 최적이다.** 네 셀 모두 여기가 봉우리다.

임계값을 내리면 버린 정답을 되찾지만 값이 너무 비싸다:

| 변경 | 얻는 것 | 잃는 것 |
|---|---|---|
| 0.54 → 0.50 | 정답 +2문항 | hard negative 방어 **−3문항** |
| 0.54 → 0.46 | 정답 +3문항 | hard negative 방어 **−10문항** |

근거 없이 답하려 드는 경우가 3~10배로 늘어난다. **임계값은 바꾸지 않는다.**

#### 부수 발견: AST+헤더는 순위만이 아니라 판정도 개선한다

0.54 에서 통과 문항이 `lines` 38/46 → `ast+header` **41/46**.
관련 청크의 유사도 자체가 올라 임계값을 더 잘 넘는다. **①에 이은 두 번째 효과다.**

#### 10.9%p 낙폭의 분해

`ast+header · hybrid`: 58.7%(27문항, 풀 순위) → **52.2%(24, 임계값 적용)** → 47.8%(22, 실제 pipeline).

- 임계값이 3문항
- 나머지 2문항은 `top_k=4` 로 자르는 것과 hnsw 근사 검색의 미세한 비결정성으로 보인다 (미확인 — 5장)

## 5. 증명되지 않은 것

**이 목록이 다음 작업의 근거다.** 아래 항목을 "확인됐다"고 말하면 안 된다.

1. **`api_test` 의 정확도** — 8문항으로는 아무것도 판정할 수 없다. 팀원 40문항 gold 대기
2. **`rag_lab`** — 아직 업로드·측정하지 않았다. 데모 시나리오 S3(규약 질의)·S4(브리핑)가 여기 걸려 있다
3. **hnsw 근사 검색의 손실** — `VSS_PG_EXACT=1` 로 질의만 다시 하면 확인된다 (재인덱싱 불필요)
4. **`top_k=4` 가 맞는가** — 재본 적 없다
5. **생성 품질** — 오늘 잰 것은 **검색까지**다. 답변이 근거를 제대로 인용하는지, 한국어가 자연스러운지는 측정하지 않았다
6. **절대 수준** — Hit@3 56.5% 는 "10문항 중 4문항은 상위 3위 안에서 정답을 못 찾는다"는 뜻이다. 개선 여지가 크다
7. **하이브리드가 다른 코퍼스에서도 무의미한가** — `fastapi-cli` 한 곳에서만 본 현상이다

## 6. 다음 단계와 판단 기준

| 다음 | 무엇이 확인되나 | 선행 조건 |
|---|---|---|
| `rag_lab` 배치·측정 | 문서 중심 코퍼스에서도 AST 가 유효한가 (지금은 코드 레포 1곳 근거) | 업로드 (바이너리 모드) |
| 팀원 40문항 gold | `api_test` 를 처음으로 판정 가능해진다 | 팀원 작업 |
| `VSS_PG_EXACT=1` 대조 | 근사 검색이 정확도를 깎는지 | 없음 — 지금 가능 |
| 프론트 연결 | 계약·화면·콜드스타트. **정확도는 확인되지 않는다** | 별칭 설정 + 서버 기동 |
| 생성 모델 bake-off | 인용 정확성·한국어 품질 | 검색이 안정된 뒤 |

**한 가지 주의**: 프론트를 붙여 질문 몇 개를 던져 보고 "잘 되네"라고 판단하면 안 된다. 그것은 표본 3~5개짜리 인상이고, 위 노이즈선 논의가 그대로 적용된다. **정확도는 gold 로만 판정한다.**

## 부록 A. 재현 방법

```bash
# EC2 에서
cd ~/vss_server && source .venv/bin/activate && set -a; source .env; set +a
python -m vss.eval run evaluation/matrices/fastapi-cli.json --note baseline

# 어디서든 (측정 결과 파일만 있으면 됨)
python -m vss.eval runs                              # 이력 한 표
python -m vss.eval sweep 20260827T061331Z --detail   # 임계값 표
python -m vss.eval report data/evaluation/runs/20260827T061331Z-254b04.json
```

## 부록 B. 이 문서가 신뢰할 수 있는 이유

- 모든 수치는 `data/evaluation/runs/*.json` 에서 나왔고, 그 파일에는 **인덱스 fingerprint · 코퍼스 commit · suite hash · 저장소 종류**가 함께 기록된다. 조건이 같을 때만 셀끼리 비교했다.
- 인덱스 4개 모두 `dirty=false` — 코퍼스가 기록된 commit 과 바이트 단위로 일치한다.
- `sweep` 은 값을 바꾸지 않는다. 표만 낸다. 임계값 변경은 사람이 결정하고 `DECISIONS` 에 남긴다.

## 부록 C. 오늘 도구에서 고친 것

실제 기계에서 처음 돌려 보며 드러난 결함들. 샌드박스에서는 드러날 수 없는 종류였다.

| 문제 | 원인 | 조치 |
|---|---|---|
| `setup_ec2.sh` 가 DB 초기화에서 죽음 | `postgres` 사용자가 `/home/<계정>` 을 통과할 수 없어 SQL 파일을 못 읽음 | 파일을 stdin 으로 전달 |
| 그 다음 `.env`·systemd 단계가 통째로 건너뛰어짐 | crontab 이 없는 기계에서 `crontab -l`·`grep -v` 가 각각 1을 반환 → `set -euo pipefail` 이 스크립트를 종료 | 실패를 흡수하도록 수정 |
| 코퍼스가 커밋과 달라짐 | WinSCP 텍스트 모드 전송 | `git checkout -- .` 로 복원, 전송 모드를 바이너리로 |
