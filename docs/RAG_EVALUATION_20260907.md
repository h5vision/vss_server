# RAG 평가 종합 보고서 — 2026-09-07

이 보고서는 8월 27일 기준선 이후에 확보한 검색 평가 결과, 평가 방식의 한계, 실패 원인 분석, 후속 구현 상태를 한자리에 정리한다. 대상은 현재 프로젝트에 저장된 자료이며, 운영 서버를 새로 조회하거나 평가를 재실행한 보고서는 아니다.

**최신 저장 실험은 2026-09-04, 분석·구현 기록은 2026-09-07까지다.** ast-v2의 검색 성능은 측정되어 있지만, ast-v3와 새 브리핑의 실제 품질은 아직 측정되지 않았다. 검색 지표를 생성 답변의 정확도로 해석해서는 안 된다.

## 1. 현재 확인할 수 있는 결론

1. 같은 9/4 평가 안에서 api-test의 ast-v2 + hybrid는 ast-v1 + hybrid보다 Hit@3가 **63.3% → 80.0%**, 정답 문항 수로 **19/30 → 24/30** 늘었다. fastapi-cli는 **58.7% → 60.9%**, **27/46 → 28/46**으로 변화가 작다.
2. 검색 방식을 고르는 기준에 따라 결과가 다르다. ast-v2에서 vector는 두 레포 모두 Hit@1이 높고, hybrid는 Hit@3가 높다. hybrid가 모든 지표에서 우세한 것은 아니다.
3. 두 레포의 원래 채점 기준이 다르다. 파일 단위로 다시 세면 fastapi-cli의 Hit@3는 **60.9% → 71.7%**가 된다. 이것은 검색 개선이 아니라 평가 기준 변경에 따른 차이다.
4. 같은 파일의 청크가 상위 결과를 많이 차지한다. 저장된 상위 5개에서 파일 중복을 제거하는 재분석은 개선 가능성을 보여준다. 다만 현재 구현의 파일당 상한은 2개이므로, 파일당 1개로 접은 분석 수치를 구현 성능으로 사용하면 안 된다.
5. 생성 답변의 정확성·충실도·환각률과 ast-v3의 개선율은 현재 자료만으로 제시할 수 없다.

수치는 아래 원본 실험과 재분석을 구분해 읽어야 한다. 1문항의 비중은 api-test 3.3%p, fastapi-cli 2.2%p다. 이 비중 자체가 통계적 유의성의 기준은 아니며, 이보다 큰 차이라고 자동으로 유의한 개선이 되는 것도 아니다.

## 3. 평가가 측정하는 것

검색 평가는 질문에 대응하는 정답 근거(gold)를 검색기가 얼마나 앞에 배치하는지 잰다. pipeline 평가는 임계값과 문맥 선택을 거친 근거를 평가한다. **두 모드 모두 LLM이 생성한 답변을 채점하는 실험은 아니다.**

| 지표 | 의미 | 주의점 |
|---|---|---|
| Hit@1·3·5 | 답 있는 문항 중 정답 근거가 상위 1·3·5위 안에 있는 비율 | gold의 경로·줄 범위 등 매칭 기준에 좌우됨 |
| MRR | 첫 정답 순위의 역수를 평균한 값, 미검색은 0 | 높을수록 정답이 앞에 있음 |
| 답가능 통과율 | 답 있는 문항에서 `has_evidence=true`인 비율 | 통과한 근거가 정답이라는 뜻은 아님 |
| no-evidence recall | 답 없는 문항을 근거 없음으로 차단한 비율 | 답변 환각률과는 다름 |
| p95 지연 | 해당 평가 모드의 기록된 처리 시간 95백분위 | LLM 답변 생성 시간이나 부하 시험 결과가 아님 |

구현 근거: [metrics.py](../vss/eval/metrics.py), [runner.py](../vss/eval/runner.py).

## 5. 기존 수치를 해석할 때 바로잡아야 할 사항

### 5.1 두 레포의 gold 판정 기준이 다르다

[ACCURACY 3절](ACCURACY.md)에 따르면 api-test는 경로와 symbol, fastapi-cli는 경로와 줄 범위를 gold로 사용했다. 이 실험의 api-test symbol 판정은 실질적으로 파일 단위 결과와 같았지만 fastapi-cli는 같은 파일을 찾아도 줄이 겹치지 않으면 오답이었다.

ast-v2 hybrid retrieval을 gold 파일 경로만으로 다시 센 결과:

| 대상 | 원래 Hit@1 | 파일 단위 Hit@1 | 원래 Hit@3 | 파일 단위 Hit@3 |
|---|---:|---:|---:|---:|
| api-test | 56.7% | 56.7% (17/30) | 80.0% | 80.0% (24/30) |
| fastapi-cli | 39.1% | 52.2% (24/46) | 60.9% | 71.7% (33/46) |

Hit@3의 레포 간 차이는 19.1%p에서 8.3%p로 줄어든다. 다만 파일을 맞히는 평가와 필요한 코드 구간을 맞히는 평가는 서로 다른 질문이다. 파일 단위 수치로 원래 값을 대체하기보다 두 지표를 함께 보고하는 편이 적절하다.

### 5.2 평가 설정과 서빙 기본값이 다르다

현재 [config.py](../vss/config.py)의 top_k 기본값은 8이지만, 두 [평가 matrix](../evaluation/matrices/)에는 여전히 4가 들어 있다. 실행 환경의 환경변수에 따라 서빙 값은 달라질 수 있으며, 여기서는 코드 기본값과 저장 실험을 비교한다.

[ACCURACY 3~4절](ACCURACY.md)에 기록된 경로 기준 재집계는 다음과 같다. **새 top_k=8 실험 결과가 아니라 저장 결과로 추정한 값**이다.

| 대상 | 기존 top_k=4에서 정답 경로 포함 | top_k=8로 넓혔을 때의 추정 |
|---|---:|---:|
| api-test | 26/30 (86.7%) | 29/30 (96.7%) |
| fastapi-cli | 29/46 (63.0%) | 32/46 (69.6%) |

fastapi-cli의 63.0%는 경로 단위 포함률이므로 4.3절의 원래 pipeline Hit@5 52.2%와 채점 기준이 다르다. 저장된 `passed_paths`와 순위로 창을 넓히는 효과를 추정했으며, 실제 서비스 정확도나 생성 답변 정확도로 인용하지 않는다.

### 5.3 코퍼스와 라벨에도 문제가 남아 있다

기존 조사 기록에서 api-test Python 파일 300개 중 19개는 BOM 때문에 ast-v2에서 줄 윈도우로 폴백했다. 이 개수는 당시 코퍼스 조사 기록이며 이번 보고서 작성에서 코퍼스를 새로 조사한 값은 아니다.

API-014·API-028·API-029는 gold에 없는 파일에도 정답 내용이 있다는 분석이 남아 있다. API-016은 README의 제한값과 코드의 제한값이 서로 달라 어떤 근거를 정답으로 삼을지도 정해야 한다. 이는 라벨을 무조건 넓히기보다, 질문의 기준과 권위 있는 원문을 명시할 문제다. 출처: [ACCURACY 3절](ACCURACY.md).

## 6. 실패 원인 재분석과 임계값

### 6.1 파일 중복을 줄이는 효과는 관측됐지만 구현 성능은 미측정이다

9/4 ast-v2 hybrid retrieval의 저장된 상위 5개 경로를 대상으로 재계산했다. 각 파일의 첫 출현만 남긴 뒤 상위 3개에 gold 경로가 있는지 센 결과다.

| 대상 | 상위 5개에 파일 중복이 있는 문항 | 기존 파일 단위 Hit@3 | 파일당 1개로 접은 Hit@3 |
|---|---:|---:|---:|
| api-test | 28/30 | 24/30 (80.0%) | 28/30 (93.3%) |
| fastapi-cli | 35/46 | 33/46 (71.7%) | 36/46 (78.3%) |

이 계산은 **저장된 top-5만 사용하는 파일 단위 분석**이다. 전체 후보를 다시 검색하거나 청크 본문을 평가한 결과가 아니다. 특히 구현은 파일당 2개를 앞에 허용하고 테스트 경로도 뒤로 보내므로, 위 수치는 ast-v3의 예상 성능이나 보장된 하한으로 사용하지 않는다.

[JOURNAL 9/7](JOURNAL.md)은 fastapi-cli 상위 3위 자리 138개 중 56개가 테스트 파일인데 gold가 테스트 파일인 문항은 없었다고 기록한다. 현재 suite에는 테스트 코드를 직접 묻는 문항이 없어, 테스트 경로 감점이 그런 질문에 주는 손해는 검증되지 않았다.

### 6.2 임계값은 현재 표본에서 레포별 상충 관계가 있다

아래는 [ACCURACY 5절](ACCURACY.md)의 저장 run sweep 기록이다. 이번 보고서에서 sweep을 새로 실행하지는 않았다.

| 대상 | threshold | 답 있는 문항 통과 | 답 없는 문항 차단 |
|---|---:|---:|---:|
| api-test | 0.54 | 30/30 | 6/10 |
| api-test | 0.56 | 30/30 | 9/10 |
| fastapi-cli | 0.52 | 42/46 | 12/15 |
| fastapi-cli | 0.54 | 41/46 | 14/15 |
| fastapi-cli | 0.56 | 39/46 | 14/15 |

이 기록에서 api-test의 0.56은 답 있는 문항 손실 없이 차단을 개선하지만, fastapi-cli에서는 답 있는 문항 2개를 추가로 잃는다. 전역 임계값을 올리면 두 레포가 함께 좋아진다고 할 근거는 없다. 같은 평가 표본으로 고른 임계값의 효과는 별도 검증 문항에서도 확인해야 한다.

| 휴리스틱 재정렬 | 파일당 상한 2, 테스트 경로 감점; auto는 v3 이상에 적용 | Hit@k·지연 변화, 테스트 질문 등에서의 손해 |
| 평가 matrix | 두 레포 모두 ast-v3 셀 추가됨 | v3 결과 run은 현재 저장 파일에 없음; top_k도 아직 4 |
| 브리핑 파이프라인 | 근거 ID 검증과 단계별 생성 구현 기록 | 실제 모델의 사실 정확도·완전성·생성 시간 |
| 생성 모델 운영 | 9/6 기록에 모델 상주·선택 경로 변경 | 모델 변경에 따른 생성 품질 개선율 |

코드 근거: [chunker.py](../vss/chunker.py), [rerank.py](../vss/rerank.py), [config.py](../vss/config.py), [api-test matrix](../evaluation/matrices/api-test.json), [fastapi-cli matrix](../evaluation/matrices/fastapi-cli.json). 운영·브리핑 상태는 [JOURNAL 9/6~9/7](JOURNAL.md) 기록을 기준으로 한다.

브리핑 기록의 가짜 모델 테스트 통과는 제어 흐름과 근거 번호 처리 등에 대한 검증이다. 근거 ID가 유효하다는 사실만으로 해당 문장이 근거에 의해 뒷받침된다고 보장되지는 않는다. 실제 생성 내용의 품질 평가가 별도로 필요하다.

## 8. 다음 평가에서 채워야 할 것

| 순서 | 작업 | 완료 시 판단할 수 있는 것 |
|---|---|---|
| 1 | gold의 경로·구간 기준과 복수 정답 정책 정리; suite 변경 시 hash 기록 | 검색 오류와 라벨 문제를 구별 |
| 2 | 실제 서빙 설정과 평가 top_k 정합성 확보; 원래 매칭과 파일 단위 지표 병기 | 문맥에 필요한 근거가 들어가는 비율 |
| 3 | 동결 코퍼스에 ast-v3 재인덱싱 후 v2·v3를 같은 조건으로 평가 | BOM 수정과 재정렬을 합친 변경의 효과 |
| 4 | 테스트 코드 질문·한 파일의 복수 근거 질문 추가, 더 많은 후보 순위 저장 | 재정렬의 손해와 실패 원인 |
| 5 | 임계값 후보를 별도 검증 문항으로 확인 | 현재 표본 밖에서도 차단과 통과가 개선되는지 |
| 6 | 생성 답변과 브리핑을 실제 모델로 채점 | 사실 정확성, 근거 충실도, 인용 적합성, 환각, 시간 |

v3 청커와 재정렬 각각의 기여를 분해하려면 재정렬 on/off 대조 셀이 추가로 필요하다. 현재 matrix는 둘을 묶어 비교하므로 전체 변경의 효과를 확인하는 데 사용할 수 있다.

`rag_lab` 평가와 Python 외 언어에 대한 청킹 검증도 기존 기록에서 미완료다. 현재 두 코드 레포 결과를 모든 문서·언어·프로젝트에 일반화하지 않는다.

## 9. 원본 확인 및 후속 실행

현재 저장 결과만 검토할 때:

```bash
python -m vss.eval runs
python -m vss.eval report data/evaluation/runs/20260904T005826Z-2f0879.json
python -m vss.eval report data/evaluation/runs/20260904T005910Z-5e6307.json
python -m vss.eval sweep 20260904T005826Z-2f0879
python -m vss.eval sweep 20260904T005910Z-5e6307
python scripts/make_status.py --no-store
```

마지막 명령은 저장소 접속 없이 로컬 `STATUS.md`를 생성한다. 위 명령은 실행 방법을 제공하는 것이며, 이번 작성 작업에서 평가나 sweep을 실행했다는 뜻은 아니다.

후속 측정은 코퍼스·인덱스·평가 설정을 확인한 환경에서 두 matrix를 실행하고 새 run JSON과 보고서를 함께 보관한다. 현재 matrix에는 v3 셀이 있으므로 해당 인덱스가 먼저 준비되어야 한다.

```bash
python -m vss.eval run evaluation/matrices/api-test.json --note ast-v3-validation
python -m vss.eval run evaluation/matrices/fastapi-cli.json --note ast-v3-validation
```

이 보고서의 표는 원본 결과를 설명하기 위한 사본이다. 인용할 때는 **run_id, 검색 모드, 채점 기준, 문항 수**를 함께 적는다. 기존 [8/27 기준선](RAG_BASELINE_20260827.md)은 당시의 판단 기록으로 보존한다.
